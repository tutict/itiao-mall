# 容量探底方案

这份文档回答一个问题：**这个应用现在能扛多少，以及天花板在哪。**

它不讲"怎么变强"，只讲"现在在哪" —— 因为没有数字的容量讨论都是修辞。

---

## 1. 为什么需要探底

门禁里的性能基线是：

| 指标 | 值 |
| --- | --- |
| 吞吐 | 173.7 req/s |
| p95 / p99 | 3.57ms / 6.11ms |
| 错误率 | 0% |
| 并发档位 | **50 VU** |

**这组数字不能回答"能扛多少"**，原因是它测的不是系统。

`tools/loadtest/scenarios/load.js` 的 `browse()` 每个迭代末尾有 `sleep(0.3)`。
50 个 VU，每个每 0.31 秒发一个请求，于是它能产生的**上限**是：

```
50 VU ÷ 0.31s ≈ 161 req/s
```

实测 173.7 req/s 与这个理论值同一量级（略高是因为还有 `order_write`
和 `login_write` 两个 write 场景在贡献少量请求）。

也就是说：**测出来的那个数，是压测脚本自己的节流阀，不是系统的容量。**
把 `load.js` 的 VU 调大也没用 —— `sleep(0.3)` 不变的话，每个 VU 仍然
只有 ~3.2 req/s，要压到 3200 req/s 需要 1000 VU，而那时 k6 自己先成为瓶颈。

所以探底必须换模型。

---

## 2. 探底模型：闭环无 sleep

`tools/loadtest/scenarios/probe.js` 的做法：

- **没有 sleep**。每个 VU 尽可能快地发下一个请求。
  这样 **VU 数才是真正的施压旋钮**，而不是被 sleep 除以的常数。
- **并发模型用 `ramping-vus`（闭环）**，不用 `constant-arrival-rate`（定速）。
  定速模型会自动加 VU 去维持目标速率，施加的负载是恒定的 ——
  那测的是"系统能不能达标"，而探底要的是"系统会不会崩"。
- **不给 `thresholds`**。探底的目标就是把系统压到出错；带阈值的话 k6 会在
  第一次越线时就以非零退出码结束，而我想要的恰恰是"越过之后继续往上推，
  看它怎么崩、崩成什么样"。

判据由 `tools/loadtest/scripts/probe-read.mjs` 读结果自己下，不交给 k6。

---

## 3. 阶梯与判据

默认阶梯 `50,150,300,600,1000` VU，每档稳态 30s、爬升 10s。

**每档独立跑一次 k6**（而不是一次连续推），原因：拐点是"某���档开始变差"，
一次性连续推的话，1000 VU 的汇总会把 300 VU 处已经发生的事盖掉 ——
最后只知道"顶到 1000 就不行了"，不知道"从哪开始不行"。

**每档之前清掉 Redis 的限流计数键**（`rl:*`）。不清的话键里累计着上一档的次数，
到后面某档突然开始 429，于是"拐点"出现在一个纯属人为的数字上。
**这个坑比看不出拐点更坏** —— 它给出一个指向错误方向的结论。

### 判据（按优先级）

| 现象 | 含义 | 该改什么 |
| --- | --- | --- |
| 错误率 > 1% 且状态码含 **500** | 系统崩了 | 查代码：连接池、SQL、行锁 |
| 错误率 > 1% 且状态码含 **429** | **限流器在工作，不是系统崩** | 换更宽限流的被测实例 |
| 错误率 0 但 p99 涨 > 5× | 已到排队拐点 | 该扩连接池 / 上缓存 |
| 最高档仍 0 错误 | **没探到天花板** | 多进程 k6 或独立压测机 |

最后一行值得强调：**"没探到天花板"是一个合法且常见的结果**，不是失败。
它意味着本机能测到的上限（某个 req/s）是**压测机**的上限 ——
把它当成系统容量，就是把工具的天花板误认成系统的天花板。

## 4. 怎么跑

```bash
# 起环境（PG + Redis + 迁移 + API + web 预览），并做一轮体检
bash scripts/dev-up.sh

# 阶梯探底（默认 50,150,300,600,1000）
bash scripts/probe-capacity.sh

# 自定义阶梯 / 每档跑久一点
STEPS=50,100,200,400 bash scripts/probe-capacity.sh
STAGE_SECONDS=45 bash scripts/probe-capacity.sh
```

### ⚠️ 被测 API 必须跑在放宽限流的配置下

```bash
RATE_LIMIT_MAX=1000000 RATE_LIMIT_AUTH_MAX=1000000 bash scripts/api.sh
```

未登录的商品读取按 **IP** 建桶（键形如
`rl:dev:read:product.read:127.0.0.1`），默认 `120 次/分钟`。
50 VU 一分钟就能打出几千次读，于是实测 **≈98% 的请求吃 429**、
`http_req_failed` 冲到 95%。

那条曲线看起来像"系统一压就崩"，**实际是限流器在工作**。
这是探底最容易得出错误结论的地方，所以脚本会在环境自检阶段先检查并提示。

### 产物

| 路径 | 内容 |
| --- | --- |
| `tools/loadtest/results/probe-step-<vus>.json` | 每档 k6 原始结果 |
| `tools/loadtest/results/probe-summary.ndjson` | 每档一行摘要 |
| `tools/loadtest/results/probe-summary.json` | 汇总（含人读表） |

## 5. 一个刻意的设计：读不到的值不填 0

`probe-read.mjs` 的 `readMetric` 在取不到值时返回 `null`，**不返回 0**。

0 是一个有意义的数字（"这个指标测出来是 0"，例如吞吐 0、错误率 0%）。
把"没找到"也返回 0，等于把"没测到"伪装成"测到了 0" ——
而这份报告的全部作用就是回答"天花板在哪"，一个假的 0 会直接把结论带偏。

同理，**一档数据必须四项齐全**（吞吐 / 错误率 / p95 / p99）才算"有数据"：

```js
out.missing = [];
if (rate === null) out.missing.push('rate');
if (failed === null) out.missing.push('failed');
if (p95 === null) out.missing.push('p95');
if (p99 === null) out.missing.push('p99');
out.hasData = out.missing.length === 0;
```

缺 p99 却算"有数据"，等于让一档残缺结果参与"系统在哪崩"的推理，
得出一个看起来有数字支撑、实际缺了关键列的结论。
这是"跳过不等于通过"的另一种形态：**不是静默跳过，而是带着残缺参与判断**。

## 6. 探底之后：什么该做，什么不该做

探底的产出是**一个数字**，不是一套架构。拿到数字之后：

### 现在就有理由做的（取决于结果）

- **读路径缓存** —— 商品列表是不可变热点。若探底显示读路径在较低档位
  就出现 p99 恶化，这是投入产出比最高的一刀。
  但前提是**缓存键设计正确**，否则会造出"缓存了脏数据"的新问题。

### 现在**没有**理由做的

- **分库分表** —— PG 的 `max_connections=200`。若探底显示拐点远高于
  200 并发，说明连接数都没用满，分库只是把"一个库的问题"变成
  "多个库的问题"，而跨库事务立刻要引入分布式事务或补偿逻辑。
- **消息队列** —— 异步化会把下单链路的库存、订单、支付回调三处
  全部变成最终一致性问题，而当前 `order_write` 的 p95 是 4.5ms，
  拆异步后用户体验只会更差。

### 把触发条件写成数字

把"什么时候该上分库分表"钉成**可判定的条件**，而不是等它变糟：

- 单库 CPU 持续 > 70%
- 单表行数 > 2000 万
- 探底拐点出现在单机、且横向扩展 API 无效（说明瓶颈在 PG 而不在应用）

到那天再上，那时它是需求而不是猜测。事后迁移比事前设计贵得多 ——
但**事前设计不需要在今天就做**。

---

## 7. 探底的边界（必须交代）

- **单机闭环压测**，量到的是"这个 API 实例 + 这台 PG"的上限，
  不是水平扩展后的总容量。
- **压测机与被测服务同机** —— CPU 会互相抢。若结果显示拐点，
  需要用独立压测机复测一次才能确认那个数字（k6 和 API 抢同一个 CPU 时，
  拐点会提前出现）。
- **数据集是固定的 20 个商品**，没有真实的多租户/多 SKU 竞争。
- 限流是**故意放宽**的，所以这份报告**不能**用来回答"限流配置对不对"。

这些限制写在这里，是为了让将来读这份数字的人不把它当成它不是的东西。

## 8. 实测结果（2026-10-11）

环境：24 逻辑核 / 16GB，PG 与 Redis 跑在同一台机器的 Docker 里（WSL2），
被测 API 是 `services/api` 的 dev 实例，限流放宽到 `RATE_LIMIT_MAX=1000000`。
每档 25s 稳态 + 8s 爬升，每档独立跑并清限流计数。

### 8.1 完整曲线

| VU | req/s | p50 | p95 | p99 | 错误率 | 状态码 |
| --- | --- | --- | --- | --- | --- | --- |
| 10 | 5778.8 | 1.15ms | 1.76ms | 2.63ms | 0% | 全 2xx |
| 50 | 9701.8 | 4.11ms | 6.53ms | 8.78ms | 0% | 全 2xx |
| 150 | 9940.3 | 13.24ms | 17.63ms | 22.59ms | 0% | 全 2xx |
| 300 | 10281.9 | 26.43ms | 32.91ms | 47.71ms | 0% | 全 2xx |
| 500 | 9946.6 | 45.70ms | 58.25ms | 84.35ms | 0% | 全 2xx |
| 600 | 10274.3 | 53.84ms | 64.37ms | 104.49ms | 0% | 全 2xx |
| 1000 | 10117.8 | 90.96ms | 109.98ms | 172.83ms | 0% | 全 2xx |

**读这张表的正确方式**：吞吐从 50 VU 起就钉在 **~10,000 req/s** 不动了，
而延迟随并发**线性增长**（p50 从 4ms 到 91ms，正好随 VU 数成比例）。

吞吐恒定 + 延迟线性 = 队列，不是容量增长。也就是说 50 VU 之后，
**每增加一个 VU 只是让队列更长，一个请求都没多处理**。

换算一下：10,000 req/s 对应每请求约 **100µs** 的独占资源时间，
而 API 进程有 24 核可用 —— 所以这不是"CPU 不够"，
是**某个单点资源把并发串行化了**。

### 8.2 三个被实验推翻的假设

探底过程中我提了三个假设，**每一个都被自己的实验推翻了**。记录在此，
因为它们的"看起来很合理"正是它们的危险之处。

#### 假设一：PG 连接池 `MaxConns = 20` 是瓶颈 —— 错

依据：`postgres.go:19` 写死 `cfg.MaxConns = 20`，且压测停止后观察到
`pg_stat_activity` 里 `idle = 20`，恰好等于池上限。

**证伪实验**：把 `MaxConns` 改成 100，重新编译成独立二进制
（`bin/api-pooltest.exe`，不动仓库源码，改完立刻按 sha256 还原并校验），
起在 :8093，跑同样的 300/600/1000 阶梯：

| 档位 | MaxConns=20 | MaxConns=100 | 差异 |
| --- | --- | --- | --- |
| 300 VU | 10074 req/s | 9772 req/s | -3.0%（噪声内） |
| 600 VU | 10274 req/s | 9629 req/s | -6.3%（略降） |
| 1000 VU | 10118 req/s | 10104 req/s | -0.1% |

池放大 5 倍，吞吐一点没涨。**连接池不是瓶颈。**

我那个推断错在：把"压测**停止后**的 `idle=20`"当成了"压测**期间**被占满的证据"。
采样时机不对，结论就整个反了。

同时确认 PG 侧确实不是瓶颈 —— 压测期间采样 `pg_stat_activity`，
`active` 始终在 1~4 之间（`max_connections=200`）。

#### 假设二：10k 是 k6 单进程压不动 —— 错

依据：300/600/1000 三档的迭代总数几乎相同（约 40 万），
看起来像"k6 在固定时间窗口里只能做这么多事"。

**证伪实验**：同一个 k6、同一个 API，只把 URL 换成不存在的路径（404 空响应）：

| 场景 | 吞吐 | p50 |
| --- | --- | --- |
| 404 空响应 | **116,988 req/s** | 4.15ms |
| 真实商品列表 | **10,104 req/s** | 92.12ms |

**11.6 倍差距。** k6 能打 11.7 万 req/s，所以它远没饱和 ——
**10k 是应用侧的天花板，不是压测机的**。

（顺带修掉了脚本里一句错误的结论：它原话是"这是压测机的上限"，
那句话是错的，已改。）

#### 假设三：1000 VU 时 55% 的失败是限流 —— 错

`http_req_failed` 报到 54.6% / 55.2%，看着像应用被打挂了。
当时 `rl:dev:read:product.read:127.0.0.1` 的 `ZCARD` 是 154434，
而失败数是 154394 —— 两者只差 40，看着像铁证。

**证伪实验**：
1. 从响应头读阈值 —— `X-Ratelimit-Limit: 1000000`。阈值是 100 万，
   计数 15 万远不到，**不可能触发限流**。`ZCARD` 只是"记录条数"，不是"计数结果"。
2. 在压测里用 `r.error` 单独计数，并打出 k6 的文本 summary 看原文。

**真实原因**：

```
Get "http://127.0.0.1:8093/api/v1/products?...":
dial tcp 127.0.0.1:8093: connectex: No connection could be made
because the target machine actively refused it.
```

而且**所有 HTTP 响应都是 200**：自定义计数器里 `4xx` 和 `5xx`
的 passes 都是 0，也就是说应用**一个错误码都没返回过**。

`actively refused` 是**内核层**的拒绝：TCP 监听队列（backlog）被打满，
Windows 直接 RST。这与应用逻辑无关 —— 它还在正常返回 200，
只是新连接进不来。

处置方向也因此相反：这种情况**不该改应用代码**，
而是降并发档位 / 加 think time / 上独立压测机（或调 backlog）。
把方向搞反的话，会为一个不存在的容量问题白改几天。

这条也写进了 `probe.js`：显式记录 `probe_transport_error`，
让"传输层失败"与"HTTP 错误码"在报告里分开。

### 8.3 结论

| 问题 | 答案 | 把握 |
| --- | --- | --- |
| 现有基线 173.7 req/s 是系统的吗 | 不是，是 `sleep(0.3)` 的节流阀 | 高（理论上限 161 与实测同量级，且换模型后实测 50 倍） |
| 应用侧吞吐天花板 | **~10,000 req/s** | 高（404 对照证明 k6 未饱和） |
| 瓶颈在哪 | **尚未定位到具体组件** | 中（已排除连接池、PG、k6 侧） |
| 错误率从哪来 | 1000 VU 时 55% 是本机 TCP backlog，非应用 | 高（有 `actively refused` 原文 + 零 4xx/5xx） |

**还没做到的一件事**：10,000 req/s 这个数字虽然可信，
但**"为什么是 10,000"在探底阶段还没有答案**。已排除的有：连接池大小、PG 饱和、
压测机 CPU。

> **2026-10-11 后续**：pprof 已接入并跑出结果，答案出来了 ——
> **限流器的 Redis Lua 往返是主要瓶颈，占 CPU 累计 35.6%，比整个业务逻辑（19.5%）还大。**
> 对照实验坐实：关掉限流后吞吐 9,879 → **13,171 req/s（+33%）**，p99 47.71 → 36.98ms。
> 详见 `docs/profiling.md` 第 9 节。

在那之前，**"10k"只能当作容量数字，不能当作优化目标**：
不知道构成就动手优化，会改到那个占大头的地方，也可能什么都改不到。

### 8.4 由此产生的地基改动优先级

探底之前的判断（"不做分库分表，做探底 + 可观测 + 读缓存"）
**不变且被强化**：

- 10k req/s 对应单实例单机，而这个量级下分库分表仍然是零收益
  （实测关掉限流也只有 13k，见 `docs/profiling.md` 第 9 节）。
- 但探底暴露了一个**之前完全看不见的缺口**：没有 pprof，
  就没有任何手段回答"时间花在哪"。
  **这比加缓存更该先做** —— 没有它，加缓存是盲改。
  ✅ 已完成（2026-10-11）：pprof 接入 + 定位到限流器是主要瓶颈。
- 读路径缓存的收益现在有了具体数字：10 VU 时 p99 是 2.63ms，
  说明单请求的服务端成本（100µs）里，没有网络与排队因素时
  是可以被压缩的；命中缓存能把这一段直接吃掉。
